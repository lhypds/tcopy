
Running under PM2
=================


`tcopy start` is enough for a laptop, but the machine running the server
usually wants two things the built-in daemon does not do: restart the process
after a crash, and bring it back after a reboot. `ecosystem.config.cjs` in the
repository root hands that job to PM2.  

This is for the server machine only. Clients keep using `tcopy start`.  


Setup
-----

Configure the machine first, so that `server.env` exists:  

```
tcopy setup          # mode: server, environment: server
```

Then start it from the checkout:  

```
./start.sh
pm2 save && pm2 startup
```

`pm2 save` records the process list and `pm2 startup` installs the boot hook,
so the server returns after a reboot.  

`./start.sh`, `./stop.sh` and `./restart.sh` pick the supervisor for you: pm2
when this machine is the server and pm2 is installed, the built-in daemon
otherwise. So the same three scripts work on the server and on your clients.
Set `TCOPY_NO_PM2=1` to force the built-in daemon here too.  

| Script                | Under pm2                                    |
|-----------------------|----------------------------------------------|
| `./start.sh`          | `pm2 startOrReload ecosystem.config.cjs`     |
| `./restart.sh`        | `pm2 restart ecosystem.config.cjs --update-env` |
| `./stop.sh`           | `pm2 stop ecosystem.config.cjs`              |
| `./stop.sh --delete`  | `pm2 delete ecosystem.config.cjs`            |

Running the pm2 commands yourself works exactly the same; the scripts only save
you from remembering which of the two supervisors this machine uses.  


Settings
--------

`PM2_NAME` and `PORT` are read from `server.env` — the file `tcopy setup`
writes, in your config directory — not from a `.env` in the checkout. See
[03_Configuration.md](03_Configuration.md) for where that lives.  

| Key        | Default | Effect                                      |
|------------|---------|---------------------------------------------|
| `PM2_NAME` | `tcopy` | Process name in `pm2 list` and `pm2 logs`   |
| `PORT`     | `5460`  | Port the server listens on                  |

Both are read when the config file is evaluated, so pass the file — not the
process name — when restarting, or the old values are reused:  

```
pm2 restart ecosystem.config.cjs
```

Changing `PM2_NAME` renames the process, and PM2 identifies processes by name.
Delete the old one first, or you end up with two:  

```
pm2 delete <old-name>
pm2 start ecosystem.config.cjs
```


Two things to avoid
-------------------

Never set `script:` to `tcopy start` or `./start.sh`. Both spawn a detached
child and exit immediately, which PM2 reads as an instant crash — it will
restart them in a loop. `ecosystem.config.cjs` names
`server_mode/server/serve.js` instead, the process that actually stays up.
(`./start.sh` calling pm2 is fine, and is the other direction.)  

Do not run `tcopy start` on a machine where PM2 owns the server. You get a
second server competing for the same port, and the loser exits without a
message because `serve.js` has no handler for the `listen` error. Use
`./start.sh`, which knows the difference.  


Logs
----

PM2 captures the server's output into its own log, reachable with
`pm2 logs "$PM2_NAME"`. The server *also* appends to `server-app.log` in the
state directory, so the same lines land in two places and neither is rotated.  

`pm2 install pm2-logrotate` takes care of PM2's copy. The state-directory copy
is yours to manage — `tcopy clear` removes it, along with the other runtime
files.
