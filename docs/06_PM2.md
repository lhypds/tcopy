
Running under PM2
=================


`tcopy start` is enough for a laptop, but a machine that keeps a server-mode
process up all day usually wants two things the built-in daemon does not do:
restart the process after a crash, and bring it back after a reboot.
`ecosystem.config.cjs` in the repository root hands that job to PM2.  

It covers both server-mode roles. `ENVIRONMENT` in `server.env` decides which
process PM2 runs:  

| `ENVIRONMENT` | Process under PM2                |
|---------------|----------------------------------|
| `server`      | `server_mode/server/serve.js`    |
| `client`      | `server_mode/client/client.js`   |

Storage mode is not covered — its clipboard watcher stays on the built-in
daemon, and starting from this file in storage mode is an error rather than a
silently wrong process.  


Setup
-----

Configure the machine first, so that `server.env` exists:  

```
tcopy setup
```

Then start it from the checkout:  

```
./start.sh
pm2 save && pm2 startup
```

`pm2 save` records the process list and `pm2 startup` installs the boot hook,
so the process returns after a reboot.  

`./start.sh`, `./stop.sh` and `./restart.sh` pick the supervisor for you: pm2
in server mode when pm2 is installed, the built-in daemon otherwise. The same
three scripts therefore work unchanged on every machine. Set `TCOPY_NO_PM2=1`
to force the built-in daemon.  

| Script                | Under pm2                                       |
|-----------------------|-------------------------------------------------|
| `./start.sh`          | `pm2 startOrReload ecosystem.config.cjs`        |
| `./restart.sh`        | Update checkout/dependencies, then `pm2 restart ecosystem.config.cjs --update-env` |
| `./stop.sh`           | `pm2 stop ecosystem.config.cjs`                 |
| `./stop.sh --delete`  | `pm2 delete ecosystem.config.cjs`               |

Running the pm2 commands yourself works exactly the same; the scripts only save
you from remembering which of the two supervisors this machine uses.  


Settings
--------

`PM2_NAME`, `ENVIRONMENT` and `PORT` are read from `server.env` — the file
`tcopy setup` writes, in your config directory — not from a `.env` in the
checkout. See [03_Configuration.md](03_Configuration.md) for where that lives.  

| Key           | Default | Effect                                        |
|---------------|---------|-----------------------------------------------|
| `PM2_NAME`    | `tcopy` | Process name in `pm2 list` and `pm2 logs`     |
| `ENVIRONMENT` | *(unset)* | Which of the two processes PM2 runs         |
| `PORT`        | `5460`  | Port the process listens on                   |

Give each machine its own `PM2_NAME` — `tcopy-server` and `tcopy-client` read
better in `pm2 list` than two entries called `tcopy`.  

All three are read when the config file is evaluated, so pass the file — not the
process name — when restarting, or the old values are reused:  

```
pm2 restart ecosystem.config.cjs
```

Changing `PM2_NAME` renames the process, and PM2 identifies processes by name.
Delete the old one first, or you end up with two:  

```
./stop.sh --delete
./start.sh
```


Two things to avoid
-------------------

Never set `script:` to `tcopy start` or `./start.sh`. Both spawn a detached
child and exit immediately, which PM2 reads as an instant crash — it will
restart them in a loop. `ecosystem.config.cjs` names the long-running process
directly instead. (`./start.sh` calling pm2 is fine, and is the other
direction.)  

Do not run `tcopy start` on a machine where PM2 owns the process. You get a
second one competing for the same port, and the loser exits without a message
because neither `serve.js` nor `client.js` handles the `listen` error. Use
`./start.sh`, which knows the difference.  


Logs
----

PM2 captures the process output into its own log, reachable with
`pm2 logs "$PM2_NAME"`. The process *also* appends to `server-app.log` or
`client-app.log` in the state directory, so the same lines land in two places
and neither is rotated.  

`pm2 install pm2-logrotate` takes care of PM2's copy. The state-directory copy
is yours to manage — `tcopy clear` removes it, along with the other runtime
files.
